## Product Overview
Multi-tenant SaaS for Indian CA firms: import clients via CSV, validate/dedupe GSTINs, verify via a GST provider, monitor GSTR-1/GSTR-3B, show an internal compliance indicator, alert, report, enforce plan quotas.

**Honest status:** the backend and a first complete frontend are built and verified **in a real browser against the in-memory store with the mock GST provider and dev sign-in** (register → verify → onboarding → dashboard → GSTINs → bulk run → team invite/accept → billing/usage, desktop and phone width, axe WCAG A/AA clean on the main screens). **Not verified:** Firestore (implementation exists, never run), a real GST provider, **real Firebase Auth in the browser** (code written, untested — no Firebase project), durable queueing. **CSV import is built and browser-verified** (messy 48-row file, plan-limit and full-plan cases, double-submit, skipped-rows download, phone width, axe clean on every step). **Not built:** reports, alerts UI/email, audit-log viewer, billing/payments, scheduled monitoring, deployment.

## Current SaaS Architecture
```
User → Firebase Auth (ID token, verified server-side)
     → Organization membership (X-Organization-Id is only a selector, verified)
     → RBAC (role from membership record, never from the request)
     → Subscription (owned by the ORGANIZATION; trial expiry ⇒ read-only)
     → Usage quota (org-wide; used + reserved; atomic hold/reserve/settle)
     → API route → Service layer → Store interface → Memory (dev/test) | Firestore (prod, unverified)

GST provider path:  CheckService → ResilientProvider (breaker → concurrency → req/min → timeout → retry) → GstProvider (mock | not-yet-implemented vendors)
Bulk path:          POST /api/bulk-checks → idempotency claim → atomic quota HOLD → job+items → queue → resumable worker → settle → finalize
```
**One CA firm = one Organization = one subscription.** Quota, seats and client limits are shared by every member.

## CSV import (milestone 5)
**Flow:** upload (drag-and-drop or file picker; .csv, ≤ 5 MB, ≤ 20,000 rows) → **map columns** (auto-guessed from headers; headerless files supported; GSTIN and client name required, email/phone optional) → **review** (server validates every row: valid / invalid / repeated in file / already a client, with plain-language reasons and a sample of each) → **confirm** (what will be added, rows skipped, client slots left; optional *verify these GSTINs right after importing* with exact usage, remaining and time) → **background import** with live progress → **result** (counts, download skipped rows, link to the verification run) and **import history**.
**Architecture rule kept: no second pipeline.** CSV → parse → normalize → validate → de-duplicate → preview → confirm → clients + GSTIN records created in background chunks → (optional) the **existing** `BulkService.create` → **existing** queue, quota hold/settle, idempotency and provider gate.
**Server guarantees (all tested):**
- The browser's analysis is never trusted: preview and start re-parse and re-validate the CSV server-side. Preview stores and consumes nothing.
- Row rules: GSTIN checksum/format, duplicates (case-insensitive) within the file, already-existing clients, missing/over-long name, invalid email or phone make the row *invalid* (with a reason) so stored data stays clean. Emails are lower-cased, phones stripped of spaces/dashes.
- **Plan limits can't be bypassed:** start refuses a file that exceeds remaining client slots (402) unless the user opts into a partial import; the limit is **re-checked per chunk** at processing time (so manual adds during an import can't push the firm over); a full plan can't start an import at all.
- **Resumable without duplicates:** validated rows are stored in 500-row chunks; client ids are deterministic (`importId + GSTIN`), progress is committed per chunk, and a fault-injected crash mid-chunk followed by resume produced exactly the right number of clients. `POST /api/imports/{id}/resume` restarts from the next chunk.
- **Idempotent:** the key is claimed *before* any state-dependent check, so a retry after completion replays the original import (explicit `Idempotency-Key`) and a keyless re-submission of a finished file is refused as "no rows can be imported" instead of double-importing. 10 simultaneous submissions ⇒ one import.
- Read-only subscriptions are blocked at start and mid-flight; the worker re-checks the requester's permission; tenants are isolated (another org's import id is simply "not found"; the same GSTIN can be imported into two firms).
- Skipped rows are kept on the import (first 1,000, flagged if truncated) and exported as CSV with a machine `reason_code` and a readable `reason`; spreadsheet formulas (`=`, `+`, `-`, `@`) are neutralised on export.
- Verification problems (plan without bulk checks, not enough quota, > 10,000 clients, subscription change) never undo the import; the result page explains and links to Bulk checks. Partial verification is opt-in.
- Upload size is enforced on the declared length **and** the actual body (chunked uploads can't bypass it).
**Not done / limits:** the original CSV is not retained (no Cloud Storage yet — only validated rows in chunks and the first 1,000 skipped rows); the file is sent as one JSON request (≤ 6 MB); no cancel button for a running import (it finishes in seconds for typical files); import runs on the in-process queue (see ISSUE-006).

## Multi-GSTIN client firms (milestone 12)
A client firm is the **billing unit** and may now hold several GSTINs (one per state registration), up to a per-plan limit. Adding GSTINs never changes the bill.
- **Model:** `Client.gstin` stays the PRIMARY GSTIN (immutable); `Client.gstins?` lists every GSTIN including the primary and is only stored once a second GSTIN is added, so existing single-GSTIN records and behaviour are untouched. Each GSTIN keeps its own `GstinRecord` (status, returns, cache) linked by `clientId`. Helpers in `src/lib/client-gstins.ts` (`clientGstins`, `panOf`, `stateNameOf` from the public GST state-code list).
- **Limits (`PlanConfig.gstinsPerClient`, the numbers from the earlier brief — change them in one place):** Free 1 · Starter 5 · Professional 10 · Firm 25 · Enterprise by contract. Error `CLIENT_GSTIN_LIMIT_REACHED` (402).
- **Rules:** a new GSTIN must share the firm's PAN (`GSTIN_PAN_MISMATCH`, 422; a different PAN is a different business and is its own client — this is also what stops unrelated businesses being bundled into one billed client), be valid, and be unused anywhere in the organization (`DUPLICATE_GSTIN`, 409, the message names the client that owns it). The primary cannot be removed (`CANNOT_REMOVE_PRIMARY_GSTIN`); archived clients must be restored first.
- **API:** `GET|POST /api/clients/{id}/gstins`, `DELETE /api/clients/{id}/gstins/{gstin}`; `POST /api/gst/check` accepts `gstin` (a specific GSTIN of the client; default primary; `GSTIN_NOT_ON_CLIENT` otherwise).
- **Everything firm-level now covers every GSTIN:** archive/restore flag all GSTIN records; rename/reassign sync all; delete removes all data; bulk checks on selected clients expand to every GSTIN (each item checks its own GSTIN, one quota unit each); the refresh planner and **scheduled verification** (`run-due`) verify every GSTIN of a due client; client search matches any GSTIN; imports/duplicate detection see all GSTINs.
- **Portfolio:** still one row per client; a multi-GSTIN row shows the **most serious** status across its GSTINs (a never-verified GSTIN does not mask a real problem), the **worst** freshness, the most recent change on any GSTIN, plus `gstins`, `gstinCount`, `statusGstin` (only present on multi-GSTIN rows; single-GSTIN rows are byte-for-byte unchanged).
- **UI:** client page "GSTINs" card (state name, status, last checked per GSTIN; select to switch the detail below; add with instant same-PAN/validity feedback; remove with confirmation), per-GSTIN "Refresh", state under each GSTIN in the clients list, pricing and billing show "GSTINs per client firm".
- **Verified:** 25 tests (service rules incl. every plan limit, PAN, duplicates across clients and organizations, archive/rename/delete sync, per-GSTIN checks and quota; portfolio merge; 7 over HTTP incl. bulk expansion with exact quota and run-due over every GSTIN; a store-contract test) with the whole suite green; in the in-app browser: client page with 3 GSTINs, switching, add (mismatched PAN blocked with the reason, matching PAN added → "Karnataka · PAN matches"), remove with confirmation, bill unchanged at ₹999 with 4 clients; axe (WCAG 2.0–2.2 + best-practice) on the client page, the add dialog, clients list and pricing at 375/768/1280 in both themes.
- **Not built:** CSV import cannot attach several GSTINs to one client (each row still creates a client; extra GSTINs are added on the client page); quick-verify "save as client GSTIN"; per-GSTIN labels/branch names (the state name is derived from the GSTIN); the dashboard "GSTINs monitored" counts GSTINs while "Total clients" counts firms (intended, not relabelled); Firestore: `gstins` array + `array-contains` lookup are written but **unverified** (no emulator, no index generated); bulk "all clients" lists per GSTIN so a firm appears once per GSTIN there.
- **Decisions I made that you may want to change:** same-PAN rule (strict; relaxing it weakens the one-firm-one-billing-unit guarantee), Free = 1 GSTIN per client, the `gstinsPerClient` numbers.

## Smart verification engine (milestone 8b — cost-aware)
Builds on the milestone 7 engine and 8 UX; goal: the fastest *trustworthy* answer while spending provider calls only when needed.
- **Freshness policy (config, UNVERIFIED against any provider's terms — `src/config/verification-policy.ts`, env `VERIFY_*`):** stored answer younger than `freshMs` (24 h) → instant, no refresh; between `freshMs` and `staleUsableMs` (7 d) → **stale-while-refresh**: shown instantly labelled "May be out of date" and the client silently asks for a live refresh; older → live required (nothing that old is shown as a result). Only registry *status* answers are ever served from storage; NOT_FOUND is always re-asked.
- **Modes (`POST /api/verify {gstin, mode}`):** `auto` (UI default: follow the policy), `refresh` (silent revalidation; **skipped, never errors**, when quota is short or the provider is unwell), `live` (explicit "Verify live now"; `force:true` is the legacy spelling). No mode (bulk) keeps the old strict behaviour. The view now carries provenance: `freshness`, `staleness`, `refreshRecommended`, `refreshSkipped` (provider_down/provider_degraded/quota), `joined`, `providerHealth`.
- **In-flight de-duplication:** concurrent live checks for the same organization + GSTIN share ONE provider call and ONE quota unit; joiners get their own request id and `joined:true`; failures and quota errors are shared; flights are cleaned up on success, failure and rejection. A bulk joiner that holds its own unit is told "cached" so the unit is released, not consumed. **In-process only** (a second server instance does not see the first's flights).
- **Provider health (`src/lib/provider-health.ts`):** rolling window → `healthy / degraded / down` (failure share, slow p95, consecutive failures, open breaker; "down" relaxes to "degraded" after a hold so recovery can be observed). *down*: auto/bulk work that needs live fails fast with MAINTENANCE (no call, no quota); stale answers still served; silent refreshes skipped; an explicit live check may probe once per `probeIntervalMs`. *degraded*: refreshes suppressed, user-needed live checks still go. NOT_FOUND counts as a healthy answer; our own rate limiting is not evidence either way. Health is process-wide, not per organization.
- **UI:** "Refreshing from the verification service…" chip → "Verified live · Updated just now"; on failure "Live refresh unavailable. Showing the stored result from …"; paused-refresh reasons; a banner when the provider is slow/unavailable; "Shared with a check already in progress".
- **Metrics:** `providerCalls`, `callsAvoided`, `joined`, `staleServed` added to `GET /api/verify/health` (which also returns `providerHealth`).
- **Verified:** 57 new tests (policy bands incl. config-driven windows, refresh/quota/read-only, health unit + engine steering, de-dup incl. failures/quota/bulk joiner/cross-org, client transitions, API `mode`); in the in-app browser with a 5 s freshness window and a 2.5 s provider delay: stored result shown instantly with "May be out of date" and "Refreshing…", then "Verified live / Updated just now"; refresh failure (fetch blocked) kept the stored result and showed "Live refresh unavailable"; 4 concurrent HTTP requests → 1 lead + 3 joined, 1 provider call (~2.5 s total), metrics matched; axe (WCAG 2.0–2.2 + best-practice) on that screen: only a pre-existing `target-size` note on the phone tab bar link under the dev-mode badge.
- **Not built (deliberately or not verified):** cross-organization shared cache and cross-org de-dup (you chose per-organization only; needs confirmation that a future provider permits reuse); priority queue and intelligent prefetch; adaptive per-GSTIN freshness; distributed de-dup/health across instances; health thresholds are guesses until measured against a real provider; `next build` was not re-run in this pass (it would have invalidated another session's running dev server) — typecheck, lint and tests were.

## End-to-end tests (milestone 16)
`npm run e2e` runs a Playwright suite (Chromium) in a real browser against the real app. It starts **its own `next dev` server** on port 3170 (`E2E_PORT`) with its own build folder (`.next-e2e`), so it never touches a developer's server or `.next`; set `E2E_REUSE=1` to reuse a server you already started. It must be a *development* server because the dev sign-in and the mock GST provider — what make the tests deterministic — are refused by production builds by design. Everything is local and fake: in-memory store, dev sign-in, mock provider.
- **Independent and parallel-safe:** every test creates its own user(s) and organization (unique emails; `createWorkspace` via the API for tests that are not about onboarding, `signInAs` seeds the dev session in `localStorage`). Mock-provider scenarios are keyed by GSTIN (`MOCK_NOT_FOUND`, `MOCK_TIMEOUT` = `e2e/gstins.ts`), never global, so one test cannot slow or break another. A warm-up (`e2e/global-setup.ts`) visits every page and API route once before the tests because `next dev` compiles routes on first request, which otherwise made the first test to touch a route time out.
- **Covered (65 tests, desktop + a Pixel 7 phone project):**

## GST cost control (milestone 13 — layered on 8b)
Goal: don't pay for the same GSTIN twice; the paid provider is the last step, never the first. Freshness / stale-while-refresh / provider-health / per-org de-duplication are milestone 8b (see above); this milestone adds the money layer on top of that pipeline (`VerificationService`, `CostGuard`).
- **Cache-first order:** local validation → own stored answer (freshness policy from 8b) → *[opt-in]* shared answer → credit protection → call limits → quota → in-flight de-duplication → paid provider → store. Every response carries `provenance`: `LIVE_PROVIDER`, `CACHE`, `SHARED_CACHE`, `DEDUPED` (`BATCH` is reserved: no batch endpoint is integrated).
- **Cross-organization sharing — OFF by default** (`VERIFY_SHARED_CACHE=on` to enable). When on: a normalized-result central cache (`sharedResults/{gstin}`: gstin, outcome, details, source, verifiedAt, provenance — **no organization/user identity, notes, tags or saved flag**; tested), cross-org in-flight de-duplication (one paid call for simultaneous requests from different organizations; the joiner gets the answer copied into its own store), and a shared answer is adopted into the requesting organization's store when served. **Enable only after the provider's terms allow caching and redistributing results between customers** — that clause is unknown (no real provider yet), as is the permitted cache TTL (`VERIFY_FRESH_MS`).
- **Credit monitor + low-credit protection:** durable counters per scope (`global`, `org:<id>`) and period (day, month): searches, paid calls, stored/shared hits, misses, joined (de-duplicated), failures, credits. The operator sets `PROVIDER_MONTHLY_CREDIT_BUDGET` (credits this month; **not read from the provider**). States: *ok* → *low* (≤ 20% left: a usable stored answer is served instead of any refresh, with a notice; stale answers stop recommending refresh) → *critical* (≤ 5%: any stored answer is served; only never-seen GSTINs may spend a credit) → *exhausted* (no paid calls: new GSTINs get `CAPACITY_LIMITED`, stored answers still served). Silent refreshes are skipped, never errors. Without a budget, protection is disabled. A credit is counted per paid call (timeouts/outages cost credits only if the provider says so; a definite NOT_FOUND counts).
- **Call limits (separate from the customer's billing quota):** per organization per minute (default 120, in-process) and per day (default 5,000, durable) → `RATE_LIMITED` with `retryAfterMs`; global per UTC day (`VERIFY_GLOBAL_PER_DAY`, off by default) → `CAPACITY_LIMITED`. Stored answers never count; bulk jobs skip the per-minute cap (the provider gate paces them) but honour the daily caps. A declined request consumes no quota and leaves no in-flight entry.
- **Explicit refresh throttle:** `VERIFY_MIN_REFRESH_MS` (default 0 = off, so an explicit live check always asks the provider, as 8b specifies). When set, refreshing an answer younger than that returns the stored answer with notice `REFRESH_TOO_SOON`.
- **Change detection:** a live answer is compared with the stored one (status, legal/trade name, taxpayer type, state, registration/cancellation dates; NOT_FOUND/UNKNOWN and newly-appearing details are never "changes"). `change {from,to,fields,deteriorated}` is returned and stored with the previous snapshot; a saved GSTIN that got worse (ACTIVE→SUSPENDED/CANCELLED/INACTIVE) raises an org alert. The result card shows a banner.
- **Dashboards:** `GET /api/verify/costs` (ADMIN/OWNER) → today/month funnel "searches → paid lookups → answered without one", avoided-call rate, credits, estimated cost (**null until `PROVIDER_COST_PER_CREDIT_INR` is set — no price is invented**); shown as "Verification activity" on `/verify` for admins. `GET /api/operator/provider` → platform-wide spend, credit state, limits, provider health, **only for user ids in `OPERATOR_UIDS`** (everyone else, owners included, gets 404; there is no platform-admin role).
- **Server-side key:** all provider access is server code (`src/providers`, `src/server`); a test scans client code for non-public `process.env` reads, provider-secret names and server imports.
- **Verified:** 36 new tests (counters per path, cost estimation, credit states and every protection rule, limits incl. window sliding / daily reset / bulk exemption / no leaked flights, throttle, sharing on/off incl. identity-free shared record and concurrent cross-org de-duplication, change detection incl. alert rules, provenance, client-secret scan) + 7 HTTP tests + a store-contract test (Firestore variant skipped). In the browser (dev server, mock provider, budget 10): after 8 credits the refresh button returned the stored result with the notice, the funnel read "9 searches → 8 paid lookups → 1 answered without one (11%)", and axe was clean in both themes (one `target-size` hit came from a zero-width pane, not the layout).
- **Not built / not verified:** **cross-instance de-duplication and the per-minute window are in-process** — several server instances can still double-pay (needs a Redis/DB lease); **no real provider, so TTL/sharing legality, billing granularity and a provider balance API are unknown** (credits are counted here, not reported by the provider); **no operator alert channel** (low-credit state is visible in the operator endpoint and as a notice to users, not pushed to anyone); **batch provider API and scheduled re-verification** are not built (milestone 14); Firestore: counter/shared collections are unverified (no emulator); no operator UI page.

## Performance (milestone 11)
Goal: feedback instantly, answers fast, never an unexplained wait — and **only claim what was measured**. There is no real GST provider, so provider latency is unknown; everything below is our own overhead, bundle size and behaviour under load. Budgets live in `config/performance.json` (latency numbers are *targets*, route sizes are enforced by `npm run perf:bundle:check`).
- **Biggest win — client JS: −43.7 KB gzip on EVERY page (≈ −30 to −42 %).** The always-loaded auth client imported `firebaseConfigured` from the module that statically imports the Firebase SDK, so ~43 KB gzip of Firebase shipped on the landing page and in dev-auth sessions even though the SDK is meant to load lazily. The check now lives in an SDK-free module (`src/lib/firebase/configured.ts`). Measured with `scripts/bundle-report.mjs` (gzip KB of the client chunks each route's manifest needs; an approximation of First Load JS, same method before/after): `/` 103.7 → 60.1, `/login` 102.7 → 59.0, `/dashboard` 121.6 → 77.9, `/verify` 140.8 → 94.0 (also lazy-loads the scanner, the concern dialog and the share-image renderer), `/bulk-checks/[id]` 141.0 → 73.2 (it only needed a badge and was pulling the whole verification UI; `OutcomeBadge` now has its own module), `/concerns` 137.1 → 70.5.
- **Server latency: fewer sequential store round trips.** Independent reads/writes in `VerificationService.verify/runLive` and `CostGuard.admit` now go out together. Critical path, measured in virtual time with every store call costing the same (`tests/perf.test.ts`): **stored lookup 6 → 3 round trips, live lookup 11 → 5** (the "before" values are from a call trace of the previous code). On a store with a 20 ms round trip that is ~60 ms / ~100 ms of overhead instead of ~120 ms / ~220 ms. Real Firestore round-trip times are **unmeasured** (no emulator/project), so the absolute saving is unknown; the reduction in round trips is exact.
- **Batched reads:** new `Store.getVerifications(orgId, gstins[])` (Firestore: `getAll`, 300 per call). Bulk preview/start, the results page join and CSV export now read stored answers per page instead of per GSTIN: previewing 2,000 GSTINs = 1 batched call instead of 2,000 single reads (asserted). On Firestore that is both latency and cost (reads are billed per document either way, but round trips fall ~300×).
- **Our pipeline overhead is small (in-memory store, instant provider, this machine):** stored lookup p50 0.04 ms / p95 0.07 ms; live lookup p50 0.03 ms / p95 0.13 ms (budget p95 ≤ 50 ms, asserted). 60 distinct lookups against a 20 ms provider finish in ~400 ms with concurrency capped at 5 (serial would be ≥ 1.2 s); 50 simultaneous lookups of one GSTIN make 1 provider call. A 3,000-GSTIN bulk run: 475 ms (~6,300 items/s) with peak concurrency 5 and exact quota accounting; scaling is linear (≈ 0.1 ms/item from 500 to 2,000 items). 5,000-row export: ~114 ms, 435 KB. The pane is hidden/throttled and the server was in dev mode, so these are indicative only.

- **Tools added:** `npm run perf:bundle` / `perf:bundle:check`; `NEXT_DIST_DIR=.next-build npm run build` builds into its own folder so it does not invalidate a running dev server (lint ignores `.next-*`); `tests/perf.test.ts` (budget coherence, round trips, overhead, concurrency, throughput; thresholds are generous so they catch accidental O(n²)/serial regressions, not small drift).

## GST verification engine (milestone 7)
**Promise:** verify a GSTIN quickly, say what the result means, and never leave the user on an unexplained spinner. A failure of *our pipeline or the provider* is never presented as a statement about the GSTIN.
- **Backend (`VerificationService`, `POST /api/verify`, `GET /api/verify/recent`, `GET /api/verify/health`):** local format + checksum validation first (free, instant, no provider call) → per-org cache (status answers only, 24 h TTL, `force` bypasses) → quota reserve → provider through the existing `ResilientProvider` under a **hard 20 s deadline** → classification → store → typed `VerificationView` (request id, outcome, details, `freshness` live/cached, `ageSeconds`, `retryable`, `retryAfterMs`, `lastKnown` stale answer on failure).
- **Outcomes:** `ACTIVE SUSPENDED CANCELLED INACTIVE UNKNOWN NOT_FOUND INVALID_GSTIN TIMEOUT MAINTENANCE RATE_LIMITED PROVIDER_ERROR NETWORK_ERROR`. Registry answers vs pipeline failures are separate classes (`src/lib/verification.ts`); every failure outcome carries the copy "This does not mean the GSTIN is fake" and a test forbids "fake"/"fraud" as a finding anywhere in the explanations. `NOT_FOUND` is a definite provider answer (new `GST_PROVIDER_NOT_FOUND`, non-retryable, doesn't trip the breaker), is never cached, and costs no quota.
- **Accounting:** same model as GST checks (1 unit per live verification, 1 provider request, no return history); cache hits, `NOT_FOUND` and non-billable failures are refunded. Cached results are still served when quota is exhausted or the subscription is read-only.
- **Client state machine (`src/lib/client/verify-machine.ts`, `use-verification.ts`):** invalid format answered locally with the reason; offline detected before any request; stages at 0.3 / 1.5 / 3 s; "Taking longer than usual" with *Keep waiting* / *Try again* at 5 s; client gives up at 25 s (after the server's 20 s deadline); stale responses from a superseded request are ignored; `online/weak/offline` network state (weak is advisory only).
- **UI (`/verify`, "Verify GSTIN" in the nav and a dashboard button):** result card with status, details, "Verified live" vs "Stored result · verified N minutes ago" + *Verify live now*, plain-language meaning and caveat, a "what we checked" checklist and *Why did this happen?* on failures, the last stored answer clearly labelled out of date, a request reference for support, recent verifications (tap to re-check). Viewers see history but cannot verify.
- **Observability (`src/lib/metrics.ts`):** per-org ring buffer (last 500) → success rate, p50/p95 (all and live-only), cache-hit, timeout, provider-error, invalid and not-found rates, outcome counts. **Process-local and non-durable** — it resets on restart and is not exported anywhere; a real deployment needs a metrics backend and alerting.
- **Verified (this milestone):** tests (below); in the in-app browser against the dev server + mock provider with injected scenarios (`MOCK_NOT_FOUND`, `MOCK_TIMEOUT`, `MOCK_DELAY_MS`): invalid, live, cached, not-found, timeout/maintenance (the breaker opened after repeated injected timeouts, as designed), offline, and the slow banner at ~5 s; axe-core (WCAG 2.0–2.2 A/AA + best-practice) at 1280 and 390 px in both themes on idle, typing hint, invalid, slow, live result, cached result, not-found and offline.
- **Not built / not verified:** a real provider (no adapter, so real latency, error shapes, billing and `NOT_FOUND` mapping are unknown); **provider fallback** (single provider only — the orchestrator seam is the `GstProvider` interface); camera/QR/OCR scanning, share card, save, fraud-report workflow (milestones 8–10 in the roadmap); Firebase-persisted history is unverified (Firestore variant of the store contract is skipped); throttled-network (2G/3G) and background/locked-phone behaviour were not tested; the circuit breaker is global, so a provider-wide outage affects every organization (and, in dev, repeated injected timeouts for one GSTIN open it for all).

## Issues

### ISSUE-005 — Provider throughput caps bulk checks
**Status: MITIGATED (design resolved; real-vendor numbers still unverified) · Priority: MEDIUM · Area: GST engine · Detected 2026-10-06 · Worked 2026-10-06**
- **Root cause:** one "GST check" = GSTIN verification + return history = two provider requests, and the provider budget (spec claims 60 requests/minute — unverified) is per request, not per check. Throughput is therefore ≈ `rpm / 2` checks/min; concurrency is not the bottleneck. Previously this limit lived as a per-call limiter inside `CheckService`, with no concurrency cap, no breaker, no Retry-After handling.
- **Impact:** 1,000-client bulk check ≈ 33 min (full) or ≈ 17 min (status-only); a 2,000-check monthly plan allowance ≈ 67 min of provider time; a firm-wide refresh of 5,000 GSTINs ≈ 2.8 h. Unbounded parallelism would trip provider 429s and burn quota on failures.
- **Solution implemented:** (1) limits are explicit config (`src/config/provider.ts`, env-driven, flagged unverified); (2) `ResilientProvider` is the single enforcement point — circuit breaker ("provider unavailable"), max-concurrency semaphore, sliding-window req/min, timeout, retry with exponential backoff + full jitter + `Retry-After`; (3) bulk work is queued, claimed atomically and processed with bounded concurrency — never `Promise.all` over a batch; (4) `includeReturns=false` halves provider requests when only status is needed; (5) `/api/bulk-checks/preview` shows the user the provider-request count and estimated duration before they commit; (6) outage ⇒ breaker opens, remaining items fail fast without provider calls, every held unit is released, and `retry-failed` re-runs them after recovery. Covered by 13 gate tests + bulk outage test.
- **Remaining limitation:** actual vendor limits/pricing unknown (all values are placeholders); the limiter is per-process (a multi-instance deployment needs a shared limiter or queue-level rate such as Cloud Tasks `maxDispatchesPerSecond`); no combined verify+returns vendor endpoint assumed.

### ISSUE-006 — Background processing is not durable; filing states are "as of last check"
Status: OPEN · Priority: HIGH (before production) · Area: Bulk / Compliance · Detected 2026-10-06
Problem: `InProcessQueue` runs workers inside the web process (unsafe on serverless/Cloud Run CPU throttling; lost on restart; resumable via `/resume` but nothing calls it automatically). Return `state` (e.g. PENDING→NOT_FILED when a due date passes) only changes when a GSTIN is re-checked.
Required fix: Cloud Tasks queue + authenticated internal worker endpoint; Cloud Scheduler monitoring job that refreshes stale GSTINs and re-classifies states.
Next action: blocked on GCP project; design is in `docs/TECH.md`.

### ISSUE-007 — Idempotency claim race (found by test, RESOLVED 2026-10-06)
Problem: 10 simultaneous identical submissions — a request that saw another's claim before its job was written treated the key as stale and released it, breaking idempotency.
Fix: a claim without a job is "in progress"; waiters re-attempt the claim (taking over instantly if the owner failed) and only steal claims older than 60 s; releases are compare-and-delete. Tested (10-way concurrent submit ⇒ exactly one job/one reservation).

### ISSUE-012 — Idempotent retries after completion failed (bulk checks AND imports) — found by test/UI, RESOLVED 2026-10-06
Problem: both services ran state-dependent checks (read-only, empty selection, "no valid rows", plan gating) *before* claiming the idempotency key. A client retrying a request that had already finished (timeout, flaky network) got an error instead of the original result — e.g. `mode: "never_checked"` re-sent with the same key found nothing left to check.
Fix: claim first (fingerprint from the request, order-insensitive), release the key on any rejection; shared helper `src/lib/idempotency.ts`. Regression tests for both services.

## Costs (all assumptions; nothing here is a verified price)

- **Firestore (assumption to verify against billing docs):** each dashboard load = ~17 count aggregations (billed ≥ 1 read each, +1 per ~1,000 matched index entries) + 2 small reads ⇒ tens of reads per load, independent of org size. Bulk job of N GSTINs ≈ N item writes + ~4 writes per item (claim, finish, check log, GSTIN record) + return docs (≈24 per GSTIN per FY, upserted on each full check) ⇒ **full checks write ~30 docs per GSTIN**; `includeReturns=false` avoids the return writes. At the spec's cited $0.90/million writes this is small relative to provider cost, but must be measured on a live project.
- **CSV import writes (assumption):** per imported client ≈ 2 documents (client + GSTIN record) + 1 counter update per 500-row chunk + chunk documents (≈ 100 KB each) + up to 1,000 skipped rows on the import record; reading the existing GSTIN set at preview/start costs one read per existing client (tracked as tech debt for very large firms). Optional verification then follows the bulk-check cost model above.

## Important Decisions
- Professional = 2,000 checks (FEATURES_SUBSCRIPTIONS + master prompt over TECH.md's 2,500).
- Subscription, quota, seats, clients belong to the Organization; paid signup ⇒ 14-day card-less trial then read-only.
- One GST check = verify (+ returns) = one usage unit, 2 provider requests (re-verify against vendor billing).
- Quota split into `used` and `reserved`; bulk holds units up front, settles each unit exactly once; failures are not charged unless the provider bills them.
- Filing `state` computed at retrieval time and stored; dashboard/list filters use denormalized fields refreshed at each check (fast, but "as of last check").
- Idempotency: explicit `Idempotency-Key` (durable) or fingerprint auto-key (only while the matching job is active).
- Settlement order finish-then-settle (crash ⇒ under-charge, reconciled at finalize; never double charge).
- Compliance indicator: `Unknown`/`API Error` ⇒ "Data Unavailable", never "inactive".

## Architecture Decisions
- **ADR-010 — Imports are a second consumer of the existing `JobQueue` and a shared idempotency helper, not a new pipeline.** Queue refs carry a `kind` (`bulk` | `import`); verification calls `BulkService.create`. Deterministic client ids + per-chunk progress make the worker resumable. Rows live in chunk documents (not the import record) to stay under document-size limits. Date 2026-10-06.
- **ADR-001** Storage abstraction over Firestore. **ADR-002** Modular monolith. **ADR-003** Aggregate `Store` instead of per-entity repos. **ADR-004** Bearer-token auth, tenant by membership. **ADR-005** Membership mirror + token-hash invitations. (see earlier milestones)
- **ADR-006 — One resilient provider gate.** Decision: all provider throughput control in `ResilientProvider`; services stay free of rate-limit logic. Reason: ISSUE-005; single enforcement point, testable with virtual clocks. Alternatives: limiter per service (scattered, what we had). Date 2026-10-06.
- **ADR-007 — Denormalize compliance onto GSTIN records.** Decision: indicator + missing/late counts + `checked` stored on the GSTIN doc at check time. Reason: dashboard/list become indexed single-field counts independent of org size. Trade-off: values are as-of-last-check; staleness tracked in ISSUE-006. Date 2026-10-06.
- **ADR-008 — Bulk = held quota + atomic item claims + resumable worker behind a `JobQueue`.** Reason: exact accounting under concurrency and crashes; swappable for Cloud Tasks. Date 2026-10-06.
- **ADR-009 — Flat return documents** (`{gstin}_{type}_{YYYYMM}`) instead of one doc per GSTIN, enabling indexed cross-GSTIN GSTR-1/3B listings. Date 2026-10-06.
